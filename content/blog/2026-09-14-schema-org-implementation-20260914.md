# 構造化データ（Schema.org）の実装でSEOと検索表示を強化する方法

検索結果を眺めていると、店舗の評価が星マークで表示されていたり、よくある質問がそのままGoogleの画面に展開されていたりする「あの表示」を見たことがある方は多いと思います。あれはリッチリザルトと呼ばれる表示形式で、構造化データを実装しているサイトだけが得られる恩恵です。

本記事では、構造化データ（Schema.org）がどういうものなのか、そしてJSON-LD形式での具体的な実装方法まで、中小企業の担当者でも取り組める内容で解説します。

---

## そもそも構造化データとは何か

Webページには文章・画像・リンクなど様々な情報が含まれていますが、Googleのクローラーはそれらを「人間が読む文章」として処理しています。つまり、「この情報が店舗の住所なのか、それとも本文中に偶然出てきた住所なのか」を文脈から類推するしかない状態です。

構造化データとは、**ページ内の情報を機械が確実に理解できる形式で明示的に記述したコード**のことです。「このテキストはビジネスの電話番号」「この数字はレビューの評点」「このページはFAQページ」といった情報を、決まった書き方でHTMLに追記します。

その書き方の世界標準となっているのがSchema.orgです。Google・Microsoft・Yahoo!・Yandexといった主要な検索エンジンが共同で策定した語彙（ボキャブラリー）で、何百種類ものデータタイプが定義されています。

---

## なぜSEO対策として構造化データが重要なのか

「構造化データを入れても順位が上がるわけではない」という話を聞いたことがある方もいるかもしれません。これは半分正しく、半分は的を射ていません。

Googleは公式に「構造化データは直接的なランキング要因ではない」と述べています。ただし、構造化データがSEOに関係ないかというと、そんなことはありません。

**間接的なSEO効果として以下が期待できます：**

- **リッチリザルトによるクリック率の向上**：星評価・FAQ・パンくずリストなどが検索結果に表示されると、同じ順位でもクリックされやすくなります
- **Googleのクロール・インデックス精度の向上**：コンテンツの意味が正確に伝わることで、適切なクエリに対してページが表示されやすくなります
- **音声検索・AIによる回答での引用**：構造化データはGoogleのAI Overview（AIによる概要）にも活用されており、ゼロクリック検索の文脈でも存在感が出てきています

検索の文脈が「情報を探す行動」から「Googleが代わりに答えを出してくれる体験」に変わりつつある今、構造化データの重要性はむしろ高まっています。

---

## JSON-LDでの実装方法：基本の書き方

構造化データの記述形式にはMicrodata・RDFa・JSON-LDの3種類がありますが、Googleが推奨しているのはJSON-LDです。HTMLの本文に埋め込まず`<script>`タグで記述できるため、既存のHTML構造に手を加えずに実装できるのが大きな利点です。

### ローカルビジネス（LocalBusiness）の実装例

店舗を持つ企業であれば、まず取り組むべき最も基本的なタイプです。

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "LocalBusiness",
  "name": "株式会社サイプレス",
  "url": "https://example.com",
  "telephone": "03-XXXX-XXXX",
  "address": {
    "@type": "PostalAddress",
    "streetAddress": "○○区○○1-2-3",
    "addressLocality": "東京都",
    "postalCode": "100-0001",
    "addressCountry": "JP"
  },
  "openingHours": "Mo-Fr 09:00-18:00"
}
</script>
```

このコードを`<head>`タグ内か、`</body>`の直前に配置するだけで実装完了です。

### FAQページへの実装例

よくある質問ページや、記事の中にQ&Aが含まれているコンテンツに使えるタイプです。うまくいくと検索結果の画面上でQ&Aが展開表示され、ページのエリアが大きくなります。

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "mainEntity": [
    {
      "@type": "Question",
      "name": "構造化データはどこに実装すればよいですか？",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "HTMLのheadタグ内、またはbodyの末尾に配置するのが一般的です。"
      }
    }
  ]
}
</script>
```

### その他の主要なSchema.orgタイプ

業種・ページ種別に応じて使い分けるといいでしょう。

| タイプ | 用途 |
|---|---|
| Article / BlogPosting | ブログ記事・コラム |
| Product | 商品ページ |
| Review / AggregateRating | レビュー・評価 |
| BreadcrumbList | パンくずリスト |
| Organization | 会社概要ページ |
| Event | セミナー・イベント情報 |

## 実装後に必ずやるべき検証ステップ

コードを書いただけで終わりにしてはいけません。記述にミスがあるとGoogleに正しく読み取ってもらえず、せっかくの実装が無駄になります。

**①Googleのリッチリザルトテストを使う**

[Google Search Console > リッチリザルトテスト](https://search.google.com/test/rich-results)にURLか直接コードを貼り付けると、構文エラーや警告を確認できます。「有効なアイテムを検出しました」と表示されれば合格です。

**②Schema.org Validatorも併用する**

[validator.schema.org](https://validator.schema.org/)はGoogleのツールとは別の観点で検証できます。両方でエラーがないことを確認しておくと安心です。

**③Google Search Consoleの「拡張」レポートを定期確認する**

実装後はSearch Consoleの左メニューにある「拡張」セクションにFAQやパンくずリストなどのレポートが表示されます。エラー数・有効数の推移を週1回程度チェックする習慣をつけましょう。

---

## よくある失敗パターンと注意点

実装で見落としやすいポイントを整理しておきます。

**・ページの実際のコンテンツと一致していないデータを書かない**
Schema.orgで記述した内容がページ上に存在しない場合、Googleのガイドライン違反となり、ペナルティを受ける可能性があります。あくまで「ページに書いてある情報を機械向けに整理する」という役割です。

**・JSONの構文エラーに気をつける**
カンマの位置・引用符の種類・括弧の閉じ忘れなど、JSON形式には厳密な書き方のルールがあります。実装後は必ずバリデーターで確認してください。

**・WordPressを使っている場合はプラグインの活用も選択肢**
「Yoast SEO」「Rank Math」などのSEOプラグインには構造化データの自動出力機能があります。ただし、詳細な設定まで確認せずに使うと意図しない内容が出力されることもあるため、生成されたコードをリッチリザルトテストで必ず確認しましょう。

---

## まとめ：構造化データは「検索結果での見え方」を設計する取り組み

構造化データの実装は、一度やれば効果が続くストック型の施策です。コンテンツの質を高める努力はもちろん大切ですが、せっかく良い情報を持っているなら、Googleと検索ユーザーの両方にきちんと伝わる形に整備しておくことが、今後の検索対策では欠かせません。

特にAI Overview（AIによる概要）の普及により、検索エンジンがページのコンテンツを「引用しやすい形」で理解できるかどうかが、これまで以上に重要な意味を持ちます。

実装に取り掛かる順序としては、**会社概要ページへのOrganization・LocalBusiness → よくある質問ページへのFAQPage → ブログ記事へのBlogPosting** の順に進めると、効果を実感しやすいでしょう。
